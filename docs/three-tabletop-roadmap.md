# 卓をthree.jsで描き直すブランチの台帳

卓の描画を、CSS 3D（preserve-3dのDOMと盤面大のcanvas）からthree.jsへ置き換える。ブランチは`feat/three-tabletop`の1本で、全部を置き換えてから1回で出す。この文書は、ブランチで作業する人へ「何が決まっているか」「どこまで進んだか」「何を後回しにしたか」を渡すための台帳で、段階が進むたびに書き足す。

## 何を目指すか

目標は「本格的な3Dフィールドゲームの見た目」で、2026-10-31に次の範囲が決まった。

| 論点                     | 決定                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| 最初の版に入れるもの     | 実時間の光と影、空と大気、起伏のある地面（新しい地形データ）、コマのglTFモデル                            |
| カメラ                   | 今の見下ろしの載せ替え、三人称の追従、一人称（ダンジョンドリィマスターモード）も同じ場面で描き直す        |
| GPU API                  | WebGPU（`three/webgpu`とTSL）を主にし、使えない端末は自動でWebGL2に切り替える                             |
| CSS 3Dの卓               | 移し終えたら消す                                                                                          |
| 地面の深さ               | 卓の面より下（川床・池・穴）まで掘れる                                                                    |
| WebGPUもWebGL2も無い端末 | 卓の場所に、描けない理由と設定の場所を出す。チャットなどは今どおり使える                                  |
| 同梱の素材               | CC0の木・岩・草のglTFを少数入れ、野外の生成と見本の部屋で使う。パックはライセンスを調べて確定してから選ぶ |
| 出し方                   | 長命ブランチ1本。見た目の変わらない下準備も先にmainへ入れない                                             |

設計の芯は次の5つ。

- 秘匿はdomainが場面に入れる物を選んで守る。見えない物はメッシュにも影にも当たり判定にも出ない。暗闇と霧は今の`bakeOverlayPlan`の結果を正とし、未踏のマスは`maskNode`で捨て、暗闇の膜は別の出力（MRT）に書いて最後の画面処理でsRGBのまま混ぜる。
- 壁で切れる松明の光は、`domain/tabletop/vision-scene/overlay-plan.ts`の可視多角形から盤面座標の「光の場」に描く。影を落とす光は品質ごとの固定の枠（高4・標準2・軽0）で選ぶ。
- 当たり判定はCPUのレイでdomainの索引を引く。GPUのIDバッファは使わない。
- 名札・ゲージ・バフ・吹き出しなどは画面空間のDOM（HUD）に残し、タグ名と`data-testid`を今と同じにする。
- 起伏のある地面の高さはコマの`posZ`に保存しない。`GravityService`が全員の端末で`posZ`を書くので、地面を入れると旧版と書き合いになる。新しい版がその場で持ち上げを足す。

段階2で、卓のカメラを`domain/tabletop/camera/table-camera.ts`の式で扱うようにした。卓に書く変換の文字列もこの式から作るので、描く値と計算に使う値の出どころは1つになる。式の正しさは、v1.74.1のビルドで実際に描かれた位置（3つの盤の形と7つの視点、`table-camera.fixture.ts`）と0.02px以内で一致することをspecで固定している。描いた視点と卓の配置は`TableCameraService`が持ち、`CoordinateService`は卓の床の上の点だけをこの式で変換する。床の上に立つ物の面（盛り上がったコマなど）は、段階4で入力を書き直すまで、今までどおりDOMの祖先をたどる。注目したコマへ視点を寄せる動きは、CSSのtransitionをやめ、同じ`ease-out`の曲線で毎フレーム書くtween（`glideBy`）にした。動いている最中も、計算に使うカメラと描かれたカメラが一致する。

段階3で、当たり判定を`domain/tabletop/pick/`に置いた。画面の点から卓の中へ伸びる視線（`tableRayOfPage`）を、物の形（凸でなくてもよい多角柱・平面の四角形・縦の円柱・床の多角形）と交差させ、目に近い順に並べる。地形は、上面の輪郭（四角はそのまま、ヘクスは花形）、斜面、回転、浮き、開いた扉の動き（`domain/tabletop/door-motion.ts`）まで形にした。`TablePickService`は物の版ごとに形を取っておき、霧に隠れた地形を外す。いまは床の上の地形だけを載せている。コマの当たりの形は、段階7でthree.jsの立ち絵と同じ配置の関数から作る。キャラクターの立ち絵はカメラを向く板やポスター表示などCSS特有の見せ方が多く、今CSSに合わせて写しても作り直しになるためだ。

当たり判定が描かれた物と合っているかは、`e2e/table-pick.spec.ts`で、CSSの卓自身の答え（`TabletopOverlapService.drawnAt`）と画面の点ごとに比べて確かめる。四角・ヘクス（縦・横）の盤にロックしていない地形を数個置き、形の縁から3px以内の点と回転の持ち手の点を除くと、食い違いは1%未満になる。当たりの形を10pxずらすと12%食い違って落ちる。テスト用のフック`window.__axeTable`（`pickAt`・`pickAllAt`・`drawnAt`・`project`・`camera`・`aliasOf`・`edgesOnPage`）は、計画では段階5の予定だったが、この比べ方のために前倒しした。自動操作のブラウザ（`navigator.webdriver`）にだけ付く。

生成したダンジョン全体で比べたときは、結果が実行ごとに2通りに分かれた。悪いほうでは食い違いの3分の2が、CSSの卓が手前のブロックより奥のブロックを前に描いて（当たり判定にも）出している点だった。Chromiumの3Dの並べ替えの取り違えで、要素を作った順番によって出たり出なかったりする。当たり判定の側は形を作り直しても同じ答えなので、この比較は正式なテストにしていない。

段階4では、ドラッグ中にポインターの下の面を探す処理を当たり判定に移した。床・絵のある壁・ホワイトボードは、面の枠から作った四角形として当たり判定に載せた。`TablePickService.faceAt`は、ポインターの下にある面の名前を返す。ドラッグの影を描くときと別の面へ移すときは、その名前で`TableSurfaceService`から面の大きさと縁からはみ出してよいかを引き、置き場所を決める。視線は、コマがぶつかる層（今は地形）でだけ止める。CSSの卓でも、つかんだ時点で`setCollidableLayer(true)`がほかの層の`pointer-events`を切っているので、規則は同じになる。ホワイトボードに貼った地形は、ボードの枠の中の形（`on-face`）として当たりを取る。以前は、ボードの中の座標のまま床の上にあるものとして扱っていた。`e2e/table-drop-faces.spec.ts`では、本物のポインター操作でコマをボード・壁・床へ移して確かめる。

途中で、固定していないボードに貼ったコマを押すとボードのドラッグも始まる既存の不具合を見つけて直した（`c52ea17ea`）。

段階4の残りでは、ドラッグ中の座標と積み重ね、ドロップの位置も、要素を使わずに求めるようにした。ドラッグ中のコマは面の名前で座標を変換する（`CoordinateService.convertToFace`）。掴んだ位置のずれを縮める割合は、要素の箱の大きさではなく、カメラの行列から求めた「その点がどれだけ小さく描かれるか」で決める。カードと山札の積み重ねは、`CardDropService`が同じ面にある山札とカードに順に問う。画像・XML・手札のカードのドロップ、他の人のカーソル、右クリックした場所への作成、盤の地面を押す操作は、`TablePickService.landingAt`が返す点を使う。視線が最初に当たった、物を置ける面の上の点である。範囲選択の枠は床の点を使う。ドラッグ中に同期オブジェクトより先に進んでいる位置と、別の面に落とすときの影の枠は`TransientPlacementService`に置いた。今のCSSの卓はこれを読まず、段階7でthree.jsの場面が読む。

回転は段階7に回した。持ち手の高さはコマの種類ごとに違い、地形は上面、キャラクターは立ち絵の板、ボードは足元にある。角度はその面の上で測るので、1つの高さで視線との交点を取ると、背の高い地形では交点が大きくずれる（2マスの高さで傾きが50°なら約120px）。持ち手を画面空間のHUDにする段階7で、各コマが持ち手の高さを渡す形にする。

移し替えの途中で、既存の不具合を2つ直した。まとめた山札が面を引き継がず、壁の上でまとめると床へ移っていた件と、素早く離したカードを山札が古い位置で判定して取り込まなかった件である。

段階5で、卓をthree.jsでcanvasに描けるようにした。描画の本体は`infrastructure/table-3d/table-3d-engine.ts`で、`WebGPURenderer`を使い、WebGPUが使えなければWebGL2で描く。変更を伝えられたあとの次のフレームでだけ描く。カメラは`tableEyeMatrix`（盤の点を目の空間へ運ぶ行列）から組む。透視は焦点距離3000pxの`PerspectiveCamera`、正射影は`OrthographicCamera`である。盤の座標（x東・y南・z上）は左手系なので、three.jsの右手系へ`(x, z, y)`と入れ替えて写す。今は無地の盤だけを描く。

`Table3dService`は、場面（`domain/tabletop/world/`の`TableWorld`）とカメラをエンジンへ渡す。エンジンは遅延のチャンクで、canvasで描く席では起動後の暇な時間に先読みし、準備ができるまで卓に覆いを出す。WebGPUもWebGL2も作れないブラウザでは、卓の場所に理由を出す。描画の文脈が失われたら新しいcanvasで作り直し、3回までにする。描き方は`?renderer=three`（WebGL2に限るなら`three-webgl2`）で切り替え、ブラウザに覚えさせる。既定は段階14まで今のCSSの卓で、canvasで描く席ではCSSの盤の絵を隠す。

three.jsを読んでよいフォルダーは`infrastructure/three-fence.spec.ts`で固定した。ダイスの囲いのspecを一般化したもので、外から読める入口は、型だけの`table-3d-port.ts`と品質の表`table-3d-quality.ts`だけになる。

確かめ方として、Playwrightに`chromium-webgl`・`mobile-webgl`・`chromium-webgpu`の3つのプロジェクトを足した。headlessのChromiumは旗なしではWebGPUのアダプターを出さないので、前の2つはWebGL2を通る。`chromium-webgpu`はS5の旗でSwiftShaderの代替アダプターを使う。`e2e/webgl/table-scene.spec.ts`は、カメラが置く盤の辺のすぐ内側と外側の色を画面の写しから読み、canvasの盤が同じ位置にあることを確かめる。盤を30pxずらすと落ちる。canvasで流すspecの決め方は、段階7の節に書いた。

エンジンのチャンクは591KB（転送135KB）で、`angular.json`の予算で警告を1.2MB、エラーを1.6MBにした。S5で`three/webgpu`だけの場面が899KBだったことからの値である。initialは段階5で約8KB増え、警告を17.56KB超えている。

段階6では、盤と地形をcanvasに描くようにした。盤の絵は、CSSの卓と同じくsRGBのまま重ねる。CSSの`bg-white/15`は背景色なので絵の下に敷き、絵の透明な所からだけ見える。ヘクスの盤は、マスごとに1pxだけ大きくした六角形で切り抜く。グリッドは、卓のコンポーネントが描いたcanvasをそのままテクスチャにする。表示の切り替えは要素の`style`の変化を見張って伝える。

地形の面は`domain/tabletop/world/block-faces.ts`で作る。上面の輪郭を、開いた扉の動きで動かし、ブロックの回転で盤の座標へ運ぶ。斜面は平らな面ごとに頂点の高さを持たせ、その下の側面は斜面に沿って上端を折る。側面は外から見て左から右へ並べるので、絵が裏返らない。伸ばして貼る絵の座標はブロック自身の枠で決めるので、回したブロックでも絵が歪まない。卓の外周の壁は、一人称の面の計画（`firstPersonWorldOf`）から取る。

霧に全部隠れた地形は、場面に入れない。一部だけ見えている四角いブロックは、見えているマスの分だけ面を作る。ヘクスと斜面のブロックは、CSSの卓と同じく丸ごと描く。

描画の呼び出しを減らすため、面を16×16マスのチャンクに分け、チャンクの中では同じ絵を同じ貼り方で着ける面を1つの形にまとめる。地形が変わったときは、その地形が入る前と後のチャンクだけを作り直す。

奥行きの分解能が足りず、盤の0.15px上に置いたグリッドが盤に負けていた。近い面を1pxから100pxにし、グリッドを`polygonOffset`で手前に寄せて直した。ヘクスの盤のマスは平面と逆の向きに並ぶので、盤とグリッドは両面で描く。

e2eの`e2e/webgl/table-terrain.spec.ts`は、地形を置いて変わった画面の点が当たり判定の答えと一致することを確かめる。グリッドを表示したとき、何もない盤の上だけが変わり、地形の上は変わらないことも、四角とヘクスの盤で確かめる。迷宮6枚（3種類の盤と、最初と回した見え方）をCSSと並べ、地形の配置が一致することを目で確かめた。

残りは2つある。灯りによる陰り（CSSは暗い所のブロックを暗く描く）は、暗闇と霧のテクスチャと合わせて段階9で扱う。それまでは、盤の暗闇と霧をCSSの重ねが上に描く。Workerで面を組む処理は、チャンクの作り直しが重いと分かってから入れる。canvasで描く席では、CSSの地形を`invisible`で隠す。`opacity`は中の立体を平らにして、押す位置がずれるので使わない。そのため段階7までは、地形を押したりドラッグしたりできない。

段階7では、コマと物をcanvasに描き、押したり動かしたりする部分を画面空間のHUDへ移した。

コマは、場面の型の「スプライト」（絵や枠を貼った四角）とコインの円盤で描く。種類ごとの配置は`domain/tabletop/world/`の純関数（`dice-symbol-sprites.ts`・`card-sprites.ts`・`character-sprites.ts`など）で作り、描画と当たり判定が同じ配置を読む。ノートの本文やマスクの切り抜きのように、ページが自分で組む部分は、要素をSVGのforeignObjectで画像にして渡す。ダイスの転がり、コインの回転、山札の混ぜ、出てくるときの弾み、多視点の自転、被弾の揺れ、撃破は、`domain/tabletop/world/piece-motions.ts`のキーフレームを`PieceMotionsService`が進めて動かす。

HUDは`#gameTable`の外の層（`table-hud`）に置く。コマのコンポーネントは、canvasで描く席では別のテンプレートの枝を描き、タグ名・`data-object-id`・`data-part`・`data-testid`は今と同じにする。位置は`HudFrameService`が書く。カメラかコマが動いたフレームでだけ、transformと大きさを書く。根はコマ全体を投影した外接矩形に置く。子は、部品の箱、部品の四隅への射影、面の上の点、部品の角、部品の辺の真ん中、2点を結ぶ線のどれかで置く。一度も置いていない要素は、置くまで隠す。押下は`canvas-presses.ts`が捕捉の段階で受け、当たり判定で別のコマや地形に当たれば、その要素へ送り直す。

回転の持ち手は、地形・ホワイトボード・範囲・光源では面の上の点のまわりで角度を測る。キャラクターを横に傾ける持ち手は、画面の上の点のまわりで測り、立ち絵の左右に置く。頭に置くと小さい立ち絵の真ん中を覆い、コマをつかめなくなったためだ。

床の重ねは2つの形に分けた。移動範囲・移動の妨げ・移動コスト・トリガーのように、ページがcanvasに塗る物は、そのcanvasを盤の上の四角としてそのまま貼る（`FloorCanvasesService`・`FloorCanvasLayer`）。交戦エリア・自由移動の道・割り込み・ターゲットの矢印・リプレイの道筋のように、ページが要素で並べる物は、画面の面（`FloorPlaneDirective`）に載せる。この面は、盤の四隅をcanvasが描く位置へ射影して置く。高度の目安は、浮いた高さから台の真ん中までの線としてHUDに置く。

環境エフェクトとエフェクト、他の人のカーソルは、まだページの3Dで描いている。ページのカメラはcanvasと同じ式で動くので、位置はずれない。段階15でCSS 3Dを消す前に、画面に投影した要素へ移す。

e2eでは、canvasのプロジェクトで卓に関わる47ファイル（237件）だけを流す（`playwright.config.ts`の`ON_THE_TABLE`）。チャットやパネルのように描き方によらないspecは、CSSの卓で1回だけ流す。このプロジェクトは、Mesaのllvmpipeが入っていればそれで描き、SwiftShaderより2割ほど速い。全件（CSS・canvas・スマホの約845件）は、手元で11.5分かかる。

段階8では、盤の地面に起伏を付けられるようにした。地面は卓の子の`ground-field`と、その子の`ground-chunk`に持つ（`domain/tabletop/ground/`）。チャンクは32×32の標本で、標本は盤の左上から0.5マスおきに並ぶ。高さは1/64マス刻みの符号つきの整数で、卓の面より下へも掘れる。塗り（草・土・岩・砂）は4つの層の重みを4ビットずつ持つ。どちらもbase64の文字列にして属性に書く。削除した識別子は再利用できないので、チャンクは消さず、平らに書き直す。

コマの`posZ`には地面の高さを入れない。地面の持ち上げは、描くときと判定するときにその場で足す。床に置いたコマは真ん中の地面の高さだけ、床に置いた地形は足元の一番低い地面の高さだけ上がる。地形の上に立つコマは、その地形の持ち上げを継ぐ。重力が書く`posZ`は今までと同じなので、地面を知らない旧版の端末と同じ部屋にいても書き合いにならない。

盤は地面の標本を頂点にした形で描く。四角の標本は左上から右下への対角線で2つの三角形に分け、高さを読む関数も同じ分け方で補間する。分け方がずれると、コマが浮くか沈む。ヘクスの盤は、マスを4つの三角形に分け、その各辺を4等分した細かい三角形の頂点に地面の高さを持たせる。塗りは頂点の色として、盤の絵とsRGBのまま混ぜる。グリッドと、移動範囲のようにcanvasに塗る床の重ねは、地面の形に沿わせて貼る。

地面は、GMのツールバーの「地面を盛る・削る・塗る」から、canvasで描く卓の上で直接いじる。盛る・削る・ならす・平らにする・塗るの5つで、ストロークごとに手元で30回まで取り消せる。`PeerCursor`に`groundProtocol`を足し、地面を知らない端末がいると、ブラシの帯でGMに知らせる。

ルールには次のように入れた。移動範囲は、隣のマスとの高低差が1マスを超える辺を通れない（障害を越える移動の種類は除く）。一人称の一歩は、立っているマスと行き先のマスの地面を比べる。移動範囲が崖を回り込んで届くマスでも、崖を直接は登れない。グリッドのない卓の移動は、4分の1マスごとに地面を読み、直前の1マスの間に1マスを超えて上り下りする所で止まる。

見通しと光では、地面を半マスの四角ごとに4分の1マス単位の高さに丸め、高さの違う四角の境目に、高いほうの高さの壁を立てる。目と灯りは地面の分だけ持ち上げる。地面の上のマスは、その地面から目の高さだけ上の点が見えるかで判定する。こうしないと、丘の手前の斜面が自分の縁に隠れる。壁の端どうしは0.01pxだけ重ねた。四角の境目がマスの真ん中を通るため、マスの真ん中どうしを結ぶ視線が壁の継ぎ目をすり抜けていた。

水は地面の上に張る。水の底より深く掘った所は、掘った地面を底にして水で満たす。

野外の生成には「地面の起伏（マス）」を足した（0〜6マス、半マス刻み）。地面の帯を切り分けるのに使う高さを標本ごとに残し、一番低い所から指定の高さまで持ち上げる。海や浅瀬のように何も置けない帯は平らに残し、町は持ち上げない。ヘクスの盤では、列のずれを平均の位置として読むので、地面が列の境目で段にならない。起伏が0なら、出力は今までと同じになる。

マップエディターには「起伏」の層と、盛る・削る・ならす・平らにするブラシを足した。層は卓と同じ形でチャンクの文字列を持ち、層が複数あれば高さを足し合わせる。卓を取り込むと、卓の地面がそのまま1つの起伏の層になる。「機能だけ反映」は、高さの変わったチャンクだけを書き、卓が着けている塗りは残す。エディターが持ち上げなくなったチャンクは平らにする。起伏の層を一度も持たなかった場面は地面について何も言わないので、卓の地面はそのまま残る。マス単位で塗る機能塗りにしなかったのは、ブラシでなめらかに盛った地面を、反映し直すたびに段々で上書きしてしまうためである。

セーブの互換は4つの経路をspecで固定した。地面のない卓は平らに読み、既存の固定値は変わらない。地面のタグを知らない版は、そのタグを読み飛ばし、卓のほかの子はそのまま残る。座標の欠けたチャンクは無視し、長さの合わない高さはデータなしとして扱う。重力は、地面があってもなくても同じ`posZ`を書く。e2eは`e2e/webgl/table-ground.spec.ts`と`e2e/webgl/map-editor-relief.spec.ts`で、本物のポインター操作で地面を盛り、コマが持ち上がること、取り消しで戻ること、エディターから卓へ渡ることを確かめる。initialは段階8の終わりで3.26MBになった。

段階8の境目の確認で、visualの撮影比較が46件中44件落ちた。基準画像は10-29（v1.73.0）に撮ったもので、mainでGMのツールバーに「シーン」のボタンが増え、ツールバーの写る画像がずれていた。v1.75.3のビルドでも同じ44件が落ちる。そこで、v1.75.3のビルドで撮った画像を基準にし直した（`8a4e6d528`）。比べる途中で、このブランチだけの退行も1つ見つけて直した（`765c1c771`）。CSSの卓で、3マスの大きさのコマのヘクスの台が、奥の半分を盤の下に描いていた。canvasのために台の輪を1つの要素の下にまとめたとき、その要素が輪を自分の平面に平らにしていたためである。迷宮の撮影では、復元の案内の帯が撮る直前にまた出て落ちることがあったので、帯を隠すようにした。

段階9では、canvasの卓を光で照らすようにした。

ページの暗闇の重ねは、canvasの席では見えないまま描き続け、2枚に分けて場面へ渡す。1枚目は霧と記憶だけで、マテリアルの`outputNode`の中で各色をsRGBに戻してから混ぜる（膜）。2枚目は暗さだけで、黒地に灯りの届く形をくり抜いたものを、光として読む。暗い卓は空の光を暗さの分だけ下げ、各点はページがその点を暗がりから持ち上げる分だけ照らす。その量はページがsRGBで描く値を線形に戻して読むので、灯りの届く盤は見下ろしでページとほぼ同じ暗さになる。ユーザーの判断（11-03）で、暗い卓は膜をかぶせるのではなく本物の光で照らす形にした。受け入れ条件の「見下ろしで今のcanvasと画素差1%未満」は、この判断で緩める。計画では膜をMRTに書いて後処理で混ぜる予定だったが、マテリアルの中でsRGBに戻して混ぜれば、トーンマッピングのない描き方では同じ答えになるので、そうした。

太陽と月は、ゲーム内時間で動く`DirectionalLight`と、空の`HemisphereLight`で描く（`domain/tabletop/world/sky-light.ts`）。上を向いた面の明るさは、直射と空の光を合わせて常に1にしたので、暗闇のない卓は今と同じ明るさのまま、時刻で壁の陰りの向きと光の色だけが変わる。three.jsのLambertは光を1/πで受けるので、強さはπ倍にした。太陽と月は地形と立ち絵の影を落とす。影の地図は、地形・盤・時刻・コマの絵が変わったときだけ描き直す。

影を落とす設定の灯りのうち、カメラが見ている盤の点から見て点数（届く広さの2乗÷距離の2乗）の高い2つを、場面が自分で照らす（`domain/tabletop/world/light-slots.ts`・`LightSlotsService`）。入れ替えは、新しい灯りが25%上回ったときだけにした。全方向の灯りは`PointLight`、円錐の灯りは`SpotLight`で、2つずつを常に場面に置き、空いた枠は強さ0にする。数が変わってシェーダーを組み直すことがないようにするためだ。ページは枠に入った灯りを暗さの絵から外し、照らすのは3Dの光に任せる。枠に入らない灯りの輝き（色）は別のcanvasに描いて加算する。揺らぎの式は`domain/tabletop/vision-scene/light-flicker.ts`に移してページと場面で共有し、揺らぐ灯りがあるときだけ50msごとに強さを書き直す。軽量表示では枠を0にする。

立ち絵の影は、立っている絵ごとに、絵を貼った板を十字に2枚置いて落とす。板は影の描画だけが見るレイヤー1に置く。カメラを向く板で影を落とすと、カメラが回るたびに影も回り、影の地図を毎回描き直すことになるためだ。canvasの卓でHUDに置いていた向きの矢印は、台の絵の中へ移して床に寝かせた（ユーザーの指摘）。HUDは何よりも手前に描くので、立ち絵の前に出ていたためである。部屋の「向きの印」の設定も見るようにした。

ユーザーのChrome 156（GPUあり・1904×1005）で、ヘクスの迷宮（シード1278372739・地形887）を測った。CDPでキーを送る往復を外し、ページの中から毎フレーム回すと、canvasの卓は回転61.7fps（95パーセンタイルのフレーム間隔17.8ms）、パン62.5fps（17.4ms）だった。CSSの卓は回転61.3fps（19.4ms）だが、回転中のGPUが1秒あたり1,023msで使い切っている。canvasの卓のメインスレッドは回転中に1フレームあたり約10msで、目標の6msを超える。手元で回転中のJSを測るとほとんど待ちだったので、時間はDOMの描画にかかっていると見ている。canvasの席でも、CSSの地形とコマを見えないまま3Dのページに残しているからだ。止まっている卓が描き直さないことは、e2eで描画の回数を数えて固定した。

段階10では、canvasの卓に空・水・霧の層・背景のレイヤーを足し、品質を選べるようにした。

始める前に調べると、canvasの席でも水、盤の下と上の背景レイヤー、空気中の霧、水中の床は、まだページの3DのDOMで描いていた。ページのDOMはcanvasより手前にあるので、水がコマの前に出ていた。そこで、空より先にこれらを場面へ移した。

品質は、表示のメニューの「卓の画質」で、自動・高・標準・軽を順に切り替える（`Table3dQualityService`・`axe.table.quality`）。この項目はcanvasの席にだけ出す。高は影を落とす灯りの枠が4つ、標準は2つ、軽は0で、軽は太陽と月の影も落とさない。

背景のレイヤー（`BoardLayers`）は、盤の形の板に絵を敷き詰め、ページと同じく1枚ずつ流す。下のレイヤーは盤の直前に、上のレイヤーはグリッドのあと・床の重ねの前に描く。流れるレイヤーがあるあいだは毎フレーム描くが、それだけのために頼んだフレームは`whenIdle`で待たない。

水（`domain/tabletop/world/table-water.ts`・`WaterLayer`）は、水のマスと側面・岸から三角形を作る。表面の色は、深さの色・濁り・水そのものの色をページと同じ順に重ね、角ごとに深さを平均して隣のマスへなめらかにつなぐ。光の網ときらめきはTSLで描き、きらめきは流れの向きに流す。表面と側面は最後に描くので、水に立つ物の水面より下は水越しに見える。天候が水中のときの床も、盤の形に敷いて光の網を流す。空気中の霧の層は、ページが描いた絵をそのまま受け取り、高さごとの板にしてゆっくり往復させる。

空（`domain/tabletop/world/sky-dome.ts`・`SkyLayer`）は、卓の設定の「空」で「ゲーム内時間で移る空」を選んだ卓だけに描く。既存の部屋は空欄なので、今の背景のままになる。空は目の周りの球で、昼の青、朝夕の暖かい光、星の出る夜と移り、太陽と月は空の光と同じ向きに出る。盤の外には地平線まで地面を敷き、`FogExp2`で遠くを地平線の色に溶かす。空のある卓では、背景の「奥」を盤の周りの輪に立てる。追う量が少ないほど遠くに立つので、カメラを動かすと遠い物らしく動く。

品質が標準と高の卓で光る物があるときは、仕上げの描画（`TablePost`・`RenderPipeline`）を通す。光るのは暗い卓の灯りの輝きだけで、それを場面全体の別の出力に書き、ブルームでにじませる。白いカードが白いだけでにじむことはない。光る物のない卓は、高の品質でないかぎりcanvasへ直接描く。高ではGTAOで隅と溝に陰をつける。はじめはマテリアルごとに光る出力を書かせたが、three.jsはそうしたマテリアルを出力の決まっていない描画先へ描くと、その出力だけを描く。canvasへ直接描くときもそうなるので、軽の品質で場面が何も描かれなくなった（`903a93a4c`で直した）。アンチエイリアスは、計画のFXAAとSMAAではなく、場面の描画先を4倍のサンプルで描く今のやり方のままにした。

途中で4つ直した。three r186は見えない灯り（`visible = false`）を灯りの一覧から外すので、空いた枠を隠すたびにシェーダーを組み直していた。空いた枠は見せたまま強さを0にし、組み直すのは品質を変えたときだけにした。ドラッグ中のコマのために盤全体の影を毎フレーム描き直していたのは、150msに1回へ間引いた（`5c69a420f`）。同じ空と同じ霧の層をもう一度渡されるたびに描き直していたので、止まっている卓が時々描き直していた（`888932509`）。部屋のサーバーのe2eは、6ワーカーではワーカーごとに起動するWorkerで機械が詰まり、部屋に入る席が待ちを越えて5〜6件落ちていた。3ワーカーにすると全件通り、時間も5.4分から3.4分に縮んだ（`4b324dd3a`）。

ユーザーのChrome 156（GPUあり・1904×1005）で、ヘクスの迷宮（地形887）を品質ごとに測った。回転とパンは、軽・標準・高のどれも62〜63fps（95パーセンタイル17〜19ms）で、暗闇を入れても同じだった。回転中のメインスレッドは1フレームあたり軽で約9ms、標準で約10ms、高で約12ms、GPUは1秒あたり軽362ms、標準490〜530ms、高565〜630msだった。5秒の窓がときどき45fpsに落ちたが、そのあいだはメインの時間も減っていて、ページが何もしていない時間だったので、計測側の入力が止まったものと見ている。

段階11では、コマと地形を3Dモデルで描けるようにした。

モデルの形式は`.glb`だけで、保存と共有は音声の形をなぞった（`core/storage/`の`ModelFile`・`ModelStorage`・`ModelSharingSystem`、`23db81446`）。目録の配り方、`BufferSharingTask`での受け渡し、部屋のサーバーへのアップロードと再試行、素材の削除、持ち主の鍵も音声と同じに動く。上限は10MBと三角形200,000個とした。三角形は、復号する前にJSONだけから、場面に置かれた回数の分を数える（`core/storage/gltf-facts.ts`）。上限を超えたモデルは取り込まず、大きすぎるファイルの通知に名前を出す。部屋の保存は、コマの`modelIdentifier`から使っているモデルを拾ってzipに入れる。

部屋のサーバー（`udonarium_axe_backend`の`feat/model-assets`、未push）は、先頭の`glTF`と版2でモデルを見分け、10MiBまで受け取る。`PROTOCOL_VERSION`は4から5に上げた（`e0b85a2c9`）。`e2e/server/models.spec.ts`で、GMがコマに付けたモデルがサーバーを通ってPLの卓に立つことを確かめた。

`GameCharacter`と`Terrain`には、モデル・大きさ・向きのずれ・待機の動き・歩きの動きの欄を足した（`76573eade`）。どれも文字列で、空欄はモデルなし・大きさ1・向き0と読む（`domain/tabletop/piece-model.ts`）。モデルはシートの「3Dモデル」の箱で選ぶか、`.glb`を読み込んで付ける。地形にモデルを付けると、当たりと判定は今の箱のまま、見た目だけがモデルになる。

モデルはコマの箱の中に収まる大きさで、足元をコマの足元に合わせて立てる（`2727c4007`）。キャラクターの箱の高さは大きさの2倍のマスにした。動きのあるモデルは、ドラッグされているあいだだけ歩きを再生し、ほかは待機の最初の姿勢で止める。止まっている卓を描き直さないためだ。動きのないモデルは、同じモデルの写しを`InstancedMesh`でまとめて描く。生成した野外の木と岩43本は、91メッシュから14メッシュになり、1回の描画の呼び出しは81回だった（`496c52ae7`）。マテリアルは場面のLambertに作り直すので、暗闇・霧・影は盤と同じにかかる。

読み込み器は、blobとdataのURLのほかは何も取り寄せない。モデルのバイトの外を指すURIは読まない。meshoptの復号器は遅延チャンクに入れ、DracoとKTX2の復号器（どちらもApache-2.0）はビルド時に`assets/decoders/`へ写す（`509eec368`）。その読み込み器と復号器のファイルは、使うモデルが来たときにだけ取り寄せる。Khronosの見本（DracoのBoxと、KTX2の絵を貼った自作の箱）で一度確かめたが、e2eにはしていない。圧縮したモデルを作る道具を手元に入れなかったためである。

同梱素材は、KenneyのNature Kit（CC0）から木・茂み・草・岩の12点を選び、`src/assets/models/nature/`に置いた（`3c3be3015`）。マップ生成の野外は、canvasの席では既定でこれらのモデルを置く。色はファイルの指定どおりに描いている。Kenneyの色は線形の値として書かれているので、見本の画像より淡い。

旧版との行き来は次のとおり。モデルの欄はコマの属性なので、旧版は受け取った属性を丸ごと持ち、自分の編集で送り直し、保存にも書く（`8989af1e4`で今の版のこの振る舞いを固定した）。旧版はモデルを知らないので、コマを今の絵で描く。旧版がzipの中の`.glb`を読むと、種類が分からないのでzipとして開こうとして失敗し、コンソールに警告を出して読み飛ばす。モデルの共有のメッセージは、旧版に受け手がないので捨てられる。

見本の部屋に同梱のモデルを置くのは、段階14に回した。CSSの卓では箱に見えるうえ、既定の部屋の配置に頼るe2eが多いためである。

段階12では、一人称と三人称を、canvasの卓と同じ場面で描けるようにした。

canvasの席では、一人称の画面が卓のcanvasを借りて（`Table3dService.lend`）、卓の場面を目の位置から描く（`baa52358c`）。カメラは一人称のCSSのカメラと同じ式（`domain/tabletop/first-person/first-person-eye.ts`）で、焦点距離は画面の幅の半分（水平90°）、手前の切り口は1/20マスにした。CSSの一人称が距離で暗くしていた分は、場面の霧（黒・12マスで0.85）で描く。のぞいているコマ自身は場面から外し、絵はすべて目に向ける。影を落とす灯りは目の立つ所から選ぶ。囲まれた部屋には天井を張り、暗い色の下向きの面にして影は落とさない。床のグリッドは一人称では描かない。一人称の画面はCSSの面を作らず、コマは押し所と名札のために見えないまま残す。ミニマップ・方位・キー・ドラッグの見回し・ターゲット・扉・明かりは、今の一人称の部品のままである。四角の迷宮（シード1278372739）でCSSの一人称と撮り比べると、壁と扉の位置は一致した。画面を閉じるとcanvasは卓へ戻る（`e2e/webgl/first-person-canvas.spec.ts`）。

途中で既存の不具合を1つ直した。canvasの卓で、自分の絵をもつ灯り（かがり火など）が何も描かれていなかった。ページは灯りの絵を背景として描き、ページが撮る印の絵にはそれが写らないためである。自分の絵がある灯りは、その絵をマスに収めて描くようにした（`d6631d42a`）。

三人称は、canvasの卓でコマのメニューの「視界と視点」にある「このコマを後ろから追う」で始める（`997b6c2bf`）。卓のカメラそのものを、コマの肩越し（縦60°）から、コマが歩くたびに計算し直す（`domain/tabletop/camera/third-person-camera.ts`・`ThirdPersonService`）。卓のカメラの式に透視の距離の欄（`perspectivePx`）を足したので、ページのコマ・HUD・当たり判定もそのまま従う。ドラッグで回り込み、ホイールで寄ったり離れたりする。コマとカメラのあいだに地形か地面があれば竿を縮め、屋内では屋根の下にとどめて天井を張る。キーは一人称と同じ（WASD・矢印・Q/E）で、Escでやめる。追うコマは席ごとにこのブラウザに覚える（`axe.table.follow`）。追うコマの名札は隠し、ほかの名札は等倍の1.25倍までにした。カメラがコマのすぐ後ろに来たら、コマを薄く描く。一人称の歩きと向き替えは、どのコマでも受ける形に広げて三人称と共有した（`4faca2ba4`）。

e2eでは、WebGPUのプロジェクトでドラッグの多いspecが30秒を超えて7件落ちていたので、WebGL2と同じ60秒にし、ワーカーを3にした（`3ce390f7f`）。

段階1で足した目印は、コマが動く要素の`data-location`（面の上の`x,y,z`）、卓の`data-camera`（位置・回転・正射影）、コインの`data-face`、扉の`data-door`、コマの`data-object-id`、キャラクターの絵の`data-part="picture"`。e2eはtransformの文字列を読むのをやめ、これらを読む（`e995dd17e`・`cf85fc0f2`）。

## 段階0で測ったこと

試作のコードはリポジトリに置かず、手元の作業用フォルダーでesbuildにより束ねて動かした。測ったのは2026-10-31、three 0.186.1、Playwright 1.64.1同梱のChromium 156、ユーザーのWindows機（NVIDIA Ampere・60Hz）のChrome 156とEdge 156。

### WebGPUとWebGL2はどこで使えるか（S0）

| ブラウザ   | GPU                      | WebGPU         | WebGL2               | three.jsが選んだ経路と暖機                                     |
| ---------- | ------------------------ | -------------- | -------------------- | -------------------------------------------------------------- |
| Chrome 156 | あり                     | 取れる         | 作れる               | WebGPU。初回661ms、2回目からはシェーダーキャッシュで138〜163ms |
| Chrome 156 | 設定で切る               | アダプターなし | ソフトウェアで作れる | WebGL2に自動で切り替わる。466ms                                |
| Chrome 156 | 切る＋ソフトウェアも禁止 | なし           | なし                 | 描画器の初期化が例外で止まる                                   |
| Edge 156   | あり                     | 取れる         | 作れる               | WebGPU。初回1,004ms                                            |
| Edge 156   | `--disable-gpu`          | アダプターなし | ソフトウェアで作れる | WebGL2に自動で切り替わる。536ms                                |

WebGPUもWebGL2も無いとthree.jsは例外で止まるので、描画器を作る前に`navigator.gpu?.requestAdapter()`と`getContext('webgl2')`で確かめ、どちらも無ければ案内を出す。ソフトウェア描画かどうかは、WebGPUは`adapter.info.isFallbackAdapter`、WebGL2は`failIfMajorPerformanceCaveat`で見る。今の`core/util/graphics-acceleration.ts`はWebGL1しか見ていないので、ここを足す。

SafariとFirefoxはまだ確かめていない。確認ページを各端末で開いてもらい、保存された結果を読む。

### headlessのWebGPUと撮影（S5）

headlessのChromiumは、`--enable-unsafe-webgpu`を付けるとSwiftShaderの代替アダプター（`isFallbackAdapter: true`）を返す。付けなければアダプターは出ず、three.jsはWebGL2に切り替わる。撮影には`--enable-features=Vulkan --use-vulkan=swiftshader`も要る。これが無いとWebGPUのcanvasが画面の合成に乗らず、撮影結果も`toDataURL`も空になる。

この起動引数で同じ場面を別々のブラウザで2回描くと、WebGPUもWebGL2も画素まで一致した。WebGPUとWebGL2（`forceWebGL`）の差は、8/255を超える画素が0.023%だった。秘匿の切り抜きに使う`material.maskNode`と`material.maskShadowNode`は2経路とも効き、計算シェーダー（`instancedArray`、`computeAsync`）もWebGL2の経路で正しい結果になった。

`three`と`three/webgpu`は同じ`three.core.js`を読み、`Mesh`や`Vector3`は実行時も同じクラスだった。圧縮後の大きさは、`three/webgpu`だけの場面で899KB（gzip 247KB）、WebGLRendererだけで535KB（gzip 133KB）、両方で1,058KB（gzip 276KB）。どれも遅延チャンクに置き、initialには入れない。

### カメラの一致（S1）

v1.74.1のビルドを、Playwrightのchromium・firefox・webkitで測った。卓の箱は盤そのものの大きさで、回転の中心は盤の中心、投影の中心は根の要素の中心にある。式は`page(p) = 根の左上 + C + 投影(d + M·(p − O))`で、Cは根の中心、Oは盤の中心、Mは変換の文字列そのもの（正射影は`scale(P/depth)`込み）。投影は、透視なら`q.xy · 3000 / (3000 − q.z)`、正射影なら素通しになる。盤の上の9点と8つの視点で、ChromiumとWebKitは差0.001px以内、Firefoxは0.014px以内だった。

dは箱のずれで、盤が画面より狭ければ0になる。盤が画面より広いと、3つのエンジンとも箱が横だけ左端に寄る。`inset-0 m-auto`の横の余白は負にならず0になり、縦は負でも中央に来るためで、`d = (max(0, (盤の幅 − 根の幅) / 2), 0)`と書ける。CSSの卓がある間はこれで一致させる。WebGLでd=0（中央）にするかは段階14で決める。

試す点を目の後ろ（盤の外の遠い点）に置くと、投影がブラウザごとにばらばらになる（Firefoxでは数千px）。一致を確かめるspecは盤の上の点だけで書く。

### 暗闇の膜の色（S2）

three.jsは、トーンマッピングとsRGB変換を画面に書く直前に掛ける。マテリアルの`outputNode`で膜を混ぜると線形のまま混ざり、今のcanvas（sRGBで重ねる）と最大53/255ずれた。濃さ0.5の黒い膜を白に重ねると、128になるはずが181になる。膜の濃さを`material.mrtNode = mrt({ veil })`で別の出力に書き、`RenderPipeline`で`renderOutput`のあとにsRGBのまま`mix`すると、差は1/255に収まった。2経路とも同じ結果だった。

水やガラスなど半透明の面がMRTの膜の出力をどう書くかは、段階6と10で決める。

### 光と地形の重さ（S3・S4）

60×60マスにブロック1,500個（3分の1はヘクス柱）、揺らぐ光40本、コマ30体、2048pxの太陽の影、MRTの膜、霧の場面を、1920×1080のWebGPUで描いた。CPUは1フレームの処理時間。

| BatchedMesh                | 2            | 毎フレーム         | 60             | 15 / 17ms     |

立ち絵の板はカメラの方を向くので、その板で影を落とすと、カメラが回るたびに影を描き直すことになる。影は、向きを変えない別の板（レイヤー1にして影の描画だけに出す）で落とす。光が複数あるので、その板は十字に組む。

GPUなしの目安として、headlessのSwiftShader（1280×720）でも測った。WebGPU・影つき2本で3.7fps（暖機17.7秒）、WebGL2・影なしで11.4fps（暖機6.4秒）だった。今のCSS 3Dは約1fps。実際のGPUなしの端末はWebGPUのアダプターが出ないので、WebGL2の経路に入る。headlessのWebGPUは暖機が長いので、普段のe2eはWebGL2の経路で回し、WebGPUの経路はvisualの撮影に絞る。

### 画面空間の名札（S7）

名前・ゲージ・バフ3つの7要素を1つの名札とし、毎フレームtransformだけを書いた。GPUありの1080pで、CPUは名札0個の2.7msから、300個で3.3ms、600個で3.6msになり、どれも60fpsを保った。奥行きで`z-index`を並べ替え、変わったときだけ書く。名札の根に付けた`will-change: transform`はGPUなしの端末で重くなるおそれがあるので、段階7で付けるかどうかを測る。

## 後回しにしたこと

- `visual-webgpu`・`visual-webgl2`の撮影は、描く物がそろう段階14で始める。
- 光の筋と光の立体（`table-vision-volume-overlay`・`table-beam-overlay`）は、まだページの3Dで描いている。ページのカメラはcanvasと同じ式で動くので位置はずれない。エフェクトと同じく、段階15でCSS 3Dを消す前に立体へ移す。
- 影の枠の入れ替えを300msで溶かすことは、まだしていない。入れ替えの瞬間に影と明るさが跳ぶのが目につくようなら足す。
- canvasの卓のメインスレッドの時間（回転中に約10ms/フレーム）は、段階15でCSSの地形とコマを消したあとに測り直し、まだ6msを超えるなら削る。暗い卓・光40本・野外の場面の実測も残っている。
- 地形の面をWorkerで組む処理は、チャンクの作り直しが重いと分かってから入れる。
- e2eで`elementFromPoint`を使う6か所（`see-through`・`hex-pedestal`・`terrain-batch`・カットイン2つ）は、CSSの卓の当たり判定そのものを確かめている。コマが当たり判定に入る段階7で、索引に問う形に書き直す。
- 環境エフェクトとエフェクト、他の人のカーソルは、段階15でCSS 3Dを消す前に、画面に投影した要素へ移す。
- 押した場所が何もない卓かどうかを、押下の要素で決めている所がある（卓のジェスチャー、移動の計画、画像のドロップの的）。canvasで描くと押下の要素が変わるので、段階5で当たり判定とcanvasを組み合わせて決める形に直す。
- `e2e/background-backdrop.spec.ts`は背景の奥のずれをtransformから読む。空のない卓では、canvasの席でもページの背景の奥を透かして見せるので、今のまま通る。CSS 3Dを消す段階15で、空のない卓の背景の奥をどう描くかと合わせて書き直す。
- 雨と雪と稲光は、canvasの席でも画面の重ね（`table-weather-overlay`）のまま描いている。重ねは盤の上の空間を画面に写した形で切り抜くので、canvasの上でも位置は合う。カメラの周りの粒にし、稲光で空の光を強めるのは、エフェクトを移すのと合わせて段階15の前に行う。
- 水の模様のうち、泥・浮きかす・浮き葉・流れの筋はまだ場面で描いていない。canvasの席の水は色と深さ、光の網、きらめき、側面、岸の波だけになる。
- 空の種類は、シーン（`BoardScene`）の見た目の項目と、野外の生成にはまだ入れていない。
- 一人称の場面の床は、まだ平らな長方形のままにしている。CSSの一人称は段階12で同じ場面のカメラに置き換えて消すので、地面の形はそのときに場面から受け取る。
- 交戦エリアや自由移動の道のように、画面の面（`FloorPlaneDirective`）に並べる床の重ねは、平らな面に載るので丘の形に沿わない。段階15でページの3Dから外すときに、地面に沿わせる。
- 地面の見通しの壁は、起伏の多い広い盤では数万本になりうる。重さを測ってから、同じ高さで並んだ壁をつなげて減らす。
- 見本の部屋に同梱のモデルを置くのは、既定をcanvasに切り替える段階14で行う。
- DracoとKTX2のモデルは、見本で一度確かめただけでe2eにしていない。圧縮したモデルを作る道具を入れるなら、そのときにe2eへ足す。
- 一人称のvisualの基準画像（`e2e/visual/first-person.spec.ts`。CSSの面を待つ）は、段階14でcanvasに撮り直す。CSSの一人称の部品（`first-person-style.ts`・`first-person-clip`・面の組み立て）は、CSSの卓と一緒に段階15で消す。
- 共有視点で入ったPLのcanvasの一人称は、その席の暗闇と霧で描く。CSSの一人称は共有したコマの視線の届く所を全部見せていた。見せすぎることはないが、見える範囲がCSSより狭いことがある。
- 一人称の光の板（灯りのまわりのにじみ）は、canvasでは暗い卓の灯りの輝きだけになる。明るい卓のかがり火のにじみは描かない。
