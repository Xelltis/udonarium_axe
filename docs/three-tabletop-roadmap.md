# 卓をthree.jsで描き直すブランチの台帳

卓の描画を、CSS 3D（preserve-3dのDOMと盤面大のcanvas）からthree.jsへ置き換える。ブランチは`feat/three-tabletop`の1本で、全部を置き換えてから1回で出す。この文書は、ブランチで作業する人へ「何が決まっているか」「どこまで進んだか」「何を後回しにしたか」を渡すための台帳で、段階が進むたびに書き足す。

## 何を目指すか

目標は「本格的な3Dフィールドゲームの見た目」で、2026-10-31に次の範囲が決まった。

| 論点                     | 決定                                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| 最初の版に入れるもの     | 実時間の光と影、空と大気、起伏のある地面（新しい地形データ）、コマのglTFモデル                            |
| カメラ                   | 今の見下ろしの載せ替え、三人称の追従、一人称（ダンジョンドリィマスターモード）も同じ場面で描き直す        |
| GPU API                  | WebGPU（`three/webgpu`とTSL）を主にし、使えない端末は自動でWebGL2に切り替える                             |
| CSS 3Dの卓               | 移し終えたら消す                                                                                          |
| 地面の深さ               | 卓の面より下（川床・池・穴）まで掘れる                                                                    |
| WebGPUもWebGL2も無い端末 | 卓の場所に、描けない理由と設定の場所を出す。チャットなどは今どおり使える                                  |
| 同梱の素材               | CC0の木・岩・草のglTFを少数入れ、野外の生成と見本の部屋で使う。パックはライセンスを調べて確定してから選ぶ |
| 出し方                   | 長命ブランチ1本。見た目の変わらない下準備も先にmainへ入れない                                             |

設計の芯は次の5つ。

- 秘匿はdomainが場面に入れる物を選んで守る。見えない物はメッシュにも影にも当たり判定にも出ない。暗闇と霧は今の`bakeOverlayPlan`の結果を正とし、未踏のマスは`maskNode`で捨て、暗闇の膜は別の出力（MRT）に書いて最後の画面処理でsRGBのまま混ぜる。
- 壁で切れる松明の光は、`domain/tabletop/vision-scene/overlay-plan.ts`の可視多角形から盤面座標の「光の場」に描く。影を落とす光は品質ごとの固定の枠（高4・標準2・軽0）で選ぶ。
- 当たり判定はCPUのレイでdomainの索引を引く。GPUのIDバッファは使わない。
- 名札・ゲージ・バフ・吹き出しなどは画面空間のDOM（HUD）に残し、タグ名と`data-testid`を今と同じにする。
- 起伏のある地面の高さはコマの`posZ`に保存しない。`GravityService`が全員の端末で`posZ`を書くので、地面を入れると旧版と書き合いになる。新しい版がその場で持ち上げを足す。

段階2で、卓のカメラを`domain/tabletop/camera/table-camera.ts`の式で扱うようにした。卓に書く変換の文字列もこの式から作るので、描く値と計算に使う値の出どころは1つになる。式の正しさは、v1.74.1のビルドで実際に描かれた位置（3つの盤の形と7つの視点、`table-camera.fixture.ts`）と0.02px以内で一致することをspecで固定している。描いた視点と卓の配置は`TableCameraService`が持ち、`CoordinateService`は卓の床の上の点だけをこの式で変換する。床の上に立つ物の面（盛り上がったコマなど）は、段階4で入力を書き直すまで、今までどおりDOMの祖先をたどる。注目したコマへ視点を寄せる動きは、CSSのtransitionをやめ、同じ`ease-out`の曲線で毎フレーム書くtween（`glideBy`）にした。動いている最中も、計算に使うカメラと描かれたカメラが一致する。

段階3で、当たり判定を`domain/tabletop/pick/`に置いた。画面の点から卓の中へ伸びる視線（`tableRayOfPage`）を、物の形（凸でなくてもよい多角柱・平面の四角形・縦の円柱・床の多角形）と交差させ、目に近い順に並べる。地形は、上面の輪郭（四角はそのまま、ヘクスは花形）、斜面、回転、浮き、開いた扉の動き（`domain/tabletop/door-motion.ts`）まで形にした。`TablePickService`は物の版ごとに形を取っておき、霧に隠れた地形を外す。いまは床の上の地形だけを載せている。コマの当たりの形は、段階7でthree.jsの立ち絵と同じ配置の関数から作る。キャラクターの立ち絵はカメラを向く板やポスター表示などCSS特有の見せ方が多く、今CSSに合わせて写しても作り直しになるためだ。

当たり判定が描かれた物と合っているかは、`e2e/table-pick.spec.ts`で、CSSの卓自身の答え（`TabletopOverlapService.drawnAt`）と画面の点ごとに比べて確かめる。四角・ヘクス（縦・横）の盤にロックしていない地形を数個置き、形の縁から3px以内の点と回転の持ち手の点を除くと、食い違いは1%未満になる。当たりの形を10pxずらすと12%食い違って落ちる。テスト用のフック`window.__axeTable`（`pickAt`・`pickAllAt`・`drawnAt`・`project`・`camera`・`aliasOf`・`edgesOnPage`）は、計画では段階5の予定だったが、この比べ方のために前倒しした。自動操作のブラウザ（`navigator.webdriver`）にだけ付く。

生成したダンジョン全体で比べたときは、結果が実行ごとに2通りに分かれた。悪いほうでは食い違いの3分の2が、CSSの卓が手前のブロックより奥のブロックを前に描いて（当たり判定にも）出している点だった。Chromiumの3Dの並べ替えの取り違えで、要素を作った順番によって出たり出なかったりする。当たり判定の側は形を作り直しても同じ答えなので、この比較は正式なテストにしていない。

段階4では、ドラッグ中にポインターの下の面を探す処理を当たり判定に移した。床・絵のある壁・ホワイトボードは、面の枠から作った四角形として当たり判定に載せた。`TablePickService.faceAt`は、ポインターの下にある面の名前を返す。ドラッグの影を描くときと別の面へ移すときは、その名前で`TableSurfaceService`から面の大きさと縁からはみ出してよいかを引き、置き場所を決める。視線は、コマがぶつかる層（今は地形）でだけ止める。CSSの卓でも、つかんだ時点で`setCollidableLayer(true)`がほかの層の`pointer-events`を切っているので、規則は同じになる。ホワイトボードに貼った地形は、ボードの枠の中の形（`on-face`）として当たりを取る。以前は、ボードの中の座標のまま床の上にあるものとして扱っていた。`e2e/table-drop-faces.spec.ts`では、本物のポインター操作でコマをボード・壁・床へ移して確かめる。

途中で、固定していないボードに貼ったコマを押すとボードのドラッグも始まる既存の不具合を見つけて直した（`c52ea17ea`）。

段階4の残りでは、ドラッグ中の座標と積み重ね、ドロップの位置も、要素を使わずに求めるようにした。ドラッグ中のコマは面の名前で座標を変換する（`CoordinateService.convertToFace`）。掴んだ位置のずれを縮める割合は、要素の箱の大きさではなく、カメラの行列から求めた「その点がどれだけ小さく描かれるか」で決める。カードと山札の積み重ねは、`CardDropService`が同じ面にある山札とカードに順に問う。画像・XML・手札のカードのドロップ、他の人のカーソル、右クリックした場所への作成、盤の地面を押す操作は、`TablePickService.landingAt`が返す点を使う。視線が最初に当たった、物を置ける面の上の点である。範囲選択の枠は床の点を使う。ドラッグ中に同期オブジェクトより先に進んでいる位置と、別の面に落とすときの影の枠は`TransientPlacementService`に置いた。今のCSSの卓はこれを読まず、段階7でthree.jsの場面が読む。

回転は段階7に回した。持ち手の高さはコマの種類ごとに違い、地形は上面、キャラクターは立ち絵の板、ボードは足元にある。角度はその面の上で測るので、1つの高さで視線との交点を取ると、背の高い地形では交点が大きくずれる（2マスの高さで傾きが50°なら約120px）。持ち手を画面空間のHUDにする段階7で、各コマが持ち手の高さを渡す形にする。

移し替えの途中で、既存の不具合を2つ直した。まとめた山札が面を引き継がず、壁の上でまとめると床へ移っていた件と、素早く離したカードを山札が古い位置で判定して取り込まなかった件である。

段階5で、卓をthree.jsでcanvasに描けるようにした。描画の本体は`infrastructure/table-3d/table-3d-engine.ts`で、`WebGPURenderer`を使い、WebGPUが使えなければWebGL2で描く。変更を伝えられたあとの次のフレームでだけ描く。カメラは`tableEyeMatrix`（盤の点を目の空間へ運ぶ行列）から組む。透視は焦点距離3000pxの`PerspectiveCamera`、正射影は`OrthographicCamera`である。盤の座標（x東・y南・z上）は左手系なので、three.jsの右手系へ`(x, z, y)`と入れ替えて写す。今は無地の盤だけを描く。

`Table3dService`は、場面（`domain/tabletop/world/`の`TableWorld`）とカメラをエンジンへ渡す。エンジンは遅延のチャンクで、canvasで描く席では起動後の暇な時間に先読みし、準備ができるまで卓に覆いを出す。WebGPUもWebGL2も作れないブラウザでは、卓の場所に理由を出す。描画の文脈が失われたら新しいcanvasで作り直し、3回までにする。描き方は`?renderer=three`（WebGL2に限るなら`three-webgl2`）で切り替え、ブラウザに覚えさせる。既定は段階14まで今のCSSの卓で、canvasで描く席ではCSSの盤の絵を隠す。

three.jsを読んでよいフォルダーは`infrastructure/three-fence.spec.ts`で固定した。ダイスの囲いのspecを一般化したもので、外から読める入口は、型だけの`table-3d-port.ts`と品質の表`table-3d-quality.ts`だけになる。

確かめ方として、Playwrightに`chromium-webgl`・`mobile-webgl`・`chromium-webgpu`の3つのプロジェクトを足した。headlessのChromiumは旗なしではWebGPUのアダプターを出さないので、前の2つはWebGL2を通る。`chromium-webgpu`はS5の旗でSwiftShaderの代替アダプターを使う。`e2e/webgl/table-scene.spec.ts`は、カメラが置く盤の辺のすぐ内側と外側の色を画面の写しから読み、canvasの盤が同じ位置にあることを確かめる。盤を30pxずらすと落ちる。canvasで描いても通るspecは`playwright.config.ts`の許可リストに足していく。

エンジンのチャンクは591KB（転送135KB）で、`angular.json`の予算で警告を1.2MB、エラーを1.6MBにした。S5で`three/webgpu`だけの場面が899KBだったことからの値である。initialは段階5で約8KB増え、警告を17.56KB超えている。

段階6では、盤と地形をcanvasに描くようにした。盤の絵は、CSSの卓と同じくsRGBのまま重ねる。CSSの`bg-white/15`は背景色なので絵の下に敷き、絵の透明な所からだけ見える。ヘクスの盤は、マスごとに1pxだけ大きくした六角形で切り抜く。グリッドは、卓のコンポーネントが描いたcanvasをそのままテクスチャにする。表示の切り替えは要素の`style`の変化を見張って伝える。

地形の面は`domain/tabletop/world/block-faces.ts`で作る。上面の輪郭を、開いた扉の動きで動かし、ブロックの回転で盤の座標へ運ぶ。斜面は平らな面ごとに頂点の高さを持たせ、その下の側面は斜面に沿って上端を折る。側面は外から見て左から右へ並べるので、絵が裏返らない。伸ばして貼る絵の座標はブロック自身の枠で決めるので、回したブロックでも絵が歪まない。卓の外周の壁は、一人称の面の計画（`firstPersonWorldOf`）から取る。

霧に全部隠れた地形は、場面に入れない。一部だけ見えている四角いブロックは、見えているマスの分だけ面を作る。ヘクスと斜面のブロックは、CSSの卓と同じく丸ごと描く。

描画の呼び出しを減らすため、面を16×16マスのチャンクに分け、チャンクの中では同じ絵を同じ貼り方で着ける面を1つの形にまとめる。地形が変わったときは、その地形が入る前と後のチャンクだけを作り直す。

奥行きの分解能が足りず、盤の0.15px上に置いたグリッドが盤に負けていた。近い面を1pxから100pxにし、グリッドを`polygonOffset`で手前に寄せて直した。ヘクスの盤のマスは平面と逆の向きに並ぶので、盤とグリッドは両面で描く。

e2eの`e2e/webgl/table-terrain.spec.ts`は、地形を置いて変わった画面の点が当たり判定の答えと一致することを確かめる。グリッドを表示したとき、何もない盤の上だけが変わり、地形の上は変わらないことも、四角とヘクスの盤で確かめる。迷宮6枚（3種類の盤と、最初と回した見え方）をCSSと並べ、地形の配置が一致することを目で確かめた。

残りは2つある。灯りによる陰り（CSSは暗い所のブロックを暗く描く）は、暗闇と霧のテクスチャと合わせて段階9で扱う。それまでは、盤の暗闇と霧をCSSの重ねが上に描く。Workerで面を組む処理は、チャンクの作り直しが重いと分かってから入れる。canvasで描く席では、CSSの地形を`invisible`で隠す。`opacity`は中の立体を平らにして、押す位置がずれるので使わない。そのため段階7までは、地形を押したりドラッグしたりできない。

段階1で足した目印は、コマが動く要素の`data-location`（面の上の`x,y,z`）、卓の`data-camera`（位置・回転・正射影）、コインの`data-face`、扉の`data-door`、コマの`data-object-id`、キャラクターの絵の`data-part="picture"`。e2eはtransformの文字列を読むのをやめ、これらを読む（`e995dd17e`・`cf85fc0f2`）。

## 段階0で測ったこと

試作のコードはリポジトリに置かず、手元の作業用フォルダーでesbuildにより束ねて動かした。測ったのは2026-10-31、three 0.186.1、Playwright 1.64.1同梱のChromium 156、ユーザーのWindows機（NVIDIA Ampere・60Hz）のChrome 156とEdge 156。

### WebGPUとWebGL2はどこで使えるか（S0）

| ブラウザ   | GPU                      | WebGPU         | WebGL2               | three.jsが選んだ経路と暖機                                     |
| ---------- | ------------------------ | -------------- | -------------------- | -------------------------------------------------------------- |
| Chrome 156 | あり                     | 取れる         | 作れる               | WebGPU。初回661ms、2回目からはシェーダーキャッシュで138〜163ms |
| Chrome 156 | 設定で切る               | アダプターなし | ソフトウェアで作れる | WebGL2に自動で切り替わる。466ms                                |
| Chrome 156 | 切る＋ソフトウェアも禁止 | なし           | なし                 | 描画器の初期化が例外で止まる                                   |
| Edge 156   | あり                     | 取れる         | 作れる               | WebGPU。初回1,004ms                                            |
| Edge 156   | `--disable-gpu`          | アダプターなし | ソフトウェアで作れる | WebGL2に自動で切り替わる。536ms                                |

WebGPUもWebGL2も無いとthree.jsは例外で止まるので、描画器を作る前に`navigator.gpu?.requestAdapter()`と`getContext('webgl2')`で確かめ、どちらも無ければ案内を出す。ソフトウェア描画かどうかは、WebGPUは`adapter.info.isFallbackAdapter`、WebGL2は`failIfMajorPerformanceCaveat`で見る。今の`core/util/graphics-acceleration.ts`はWebGL1しか見ていないので、ここを足す。

SafariとFirefoxはまだ確かめていない。確認ページを各端末で開いてもらい、保存された結果を読む。

### headlessのWebGPUと撮影（S5）

headlessのChromiumは、`--enable-unsafe-webgpu`を付けるとSwiftShaderの代替アダプター（`isFallbackAdapter: true`）を返す。付けなければアダプターは出ず、three.jsはWebGL2に切り替わる。撮影には`--enable-features=Vulkan --use-vulkan=swiftshader`も要る。これが無いとWebGPUのcanvasが画面の合成に乗らず、撮影結果も`toDataURL`も空になる。

この起動引数で同じ場面を別々のブラウザで2回描くと、WebGPUもWebGL2も画素まで一致した。WebGPUとWebGL2（`forceWebGL`）の差は、8/255を超える画素が0.023%だった。秘匿の切り抜きに使う`material.maskNode`と`material.maskShadowNode`は2経路とも効き、計算シェーダー（`instancedArray`、`computeAsync`）もWebGL2の経路で正しい結果になった。

`three`と`three/webgpu`は同じ`three.core.js`を読み、`Mesh`や`Vector3`は実行時も同じクラスだった。圧縮後の大きさは、`three/webgpu`だけの場面で899KB（gzip 247KB）、WebGLRendererだけで535KB（gzip 133KB）、両方で1,058KB（gzip 276KB）。どれも遅延チャンクに置き、initialには入れない。

### カメラの一致（S1）

v1.74.1のビルドを、Playwrightのchromium・firefox・webkitで測った。卓の箱は盤そのものの大きさで、回転の中心は盤の中心、投影の中心は根の要素の中心にある。式は`page(p) = 根の左上 + C + 投影(d + M·(p − O))`で、Cは根の中心、Oは盤の中心、Mは変換の文字列そのもの（正射影は`scale(P/depth)`込み）。投影は、透視なら`q.xy · 3000 / (3000 − q.z)`、正射影なら素通しになる。盤の上の9点と8つの視点で、ChromiumとWebKitは差0.001px以内、Firefoxは0.014px以内だった。

dは箱のずれで、盤が画面より狭ければ0になる。盤が画面より広いと、3つのエンジンとも箱が横だけ左端に寄る。`inset-0 m-auto`の横の余白は負にならず0になり、縦は負でも中央に来るためで、`d = (max(0, (盤の幅 − 根の幅) / 2), 0)`と書ける。CSSの卓がある間はこれで一致させる。WebGLでd=0（中央）にするかは段階14で決める。

試す点を目の後ろ（盤の外の遠い点）に置くと、投影がブラウザごとにばらばらになる（Firefoxでは数千px）。一致を確かめるspecは盤の上の点だけで書く。

### 暗闇の膜の色（S2）

three.jsは、トーンマッピングとsRGB変換を画面に書く直前に掛ける。マテリアルの`outputNode`で膜を混ぜると線形のまま混ざり、今のcanvas（sRGBで重ねる）と最大53/255ずれた。濃さ0.5の黒い膜を白に重ねると、128になるはずが181になる。膜の濃さを`material.mrtNode = mrt({ veil })`で別の出力に書き、`RenderPipeline`で`renderOutput`のあとにsRGBのまま`mix`すると、差は1/255に収まった。2経路とも同じ結果だった。

水やガラスなど半透明の面がMRTの膜の出力をどう書くかは、段階6と10で決める。

### 光と地形の重さ（S3・S4）

60×60マスにブロック1,500個（3分の1はヘクス柱）、揺らぐ光40本、コマ30体、2048pxの太陽の影、MRTの膜、霧の場面を、1920×1080のWebGPUで描いた。CPUは1フレームの処理時間。

| 地形                       | 影つきの松明 | 影の描き直し       | fps            | CPU p50 / p95 |
| -------------------------- | ------------ | ------------------ | -------------- | ------------- |
| 1個ずつのメッシュ          | 2            | 毎フレーム         | 5.1            | 測っていない  |
| チャンク（16×16マス×材質） | 2            | 毎フレーム         | 60             | 7.8 / 9.1ms   |
| BatchedMesh                | 2            | 毎フレーム         | 60             | 15 / 17ms     |
| チャンク                   | 4（512px）   | 毎フレーム         | 60（4Kでも60） | 11.7 / 14.1ms |
| チャンク                   | 2            | 光が動いたときだけ | 60             | 1.9 / 2.6ms   |
| チャンク                   | 4（512px）   | 光が動いたときだけ | 60             | 2.1 / 4.4ms   |
| BatchedMesh                | 4（512px）   | 光が動いたときだけ | 60             | 1.9 / 7.1ms   |
| チャンク、WebGL2に強制     | 4（512px）   | 光が動いたときだけ | 60             | 2.5 / 4.7ms   |

GPUは4Kでも余裕があり、律速はCPU（描画呼び出しの数）にある。地形を1個ずつ描くと描画呼び出しが多すぎてCPUが追いつかないので、チャンクにまとめる。BatchedMeshはp95が跳ねるので使わない。影の地図は、光か近くの物が動いたときだけ描き直す（`shadow.autoUpdate = false`と`needsUpdate`）。影つきの光の枠を30〜40回入れ替え、40本を揺らしても、暖機のあとにシェーダーを組み直した回数は0だった（WebGPU・WebGL2とも）。

立ち絵の板はカメラの方を向くので、その板で影を落とすと、カメラが回るたびに影を描き直すことになる。影は、向きを変えない別の板（レイヤー1にして影の描画だけに出す）で落とす。光が複数あるので、その板は十字に組む。

GPUなしの目安として、headlessのSwiftShader（1280×720）でも測った。WebGPU・影つき2本で3.7fps（暖機17.7秒）、WebGL2・影なしで11.4fps（暖機6.4秒）だった。今のCSS 3Dは約1fps。実際のGPUなしの端末はWebGPUのアダプターが出ないので、WebGL2の経路に入る。headlessのWebGPUは暖機が長いので、普段のe2eはWebGL2の経路で回し、WebGPUの経路はvisualの撮影に絞る。

### 画面の後処理（S6）

| 経路                                 | 後処理             | fps  | CPU p50 / p95 |
| ------------------------------------ | ------------------ | ---- | ------------- |
| GPU・1080p・影つき2本                | ブルーム＋FXAA     | 60   | 2.7 / 3.4ms   |
| GPU・1080p・影つき4本                | AO＋ブルーム＋SMAA | 60   | 3.0 / 5.0ms   |
| GPU・4K・影つき4本                   | AO＋ブルーム＋SMAA | 60   | 3.1 / 5.2ms   |
| SwiftShader・720p・WebGL2・影なし    | 膜の合成だけ       | 11.4 | 測っていない  |
| SwiftShader・720p・WebGL2・影なし    | ブルーム＋FXAA     | 7.1  | 測っていない  |
| SwiftShader・720p・WebGL2・影つき2本 | AO＋ブルーム＋SMAA | 2.3  | 測っていない  |

並びは「場面（MRTで色・膜・法線）→AO→ブルーム→`renderOutput`→膜をsRGBで混ぜる→AA」。膜をAAの前に混ぜるので、膜の縁もなめらかになる。品質の表は、高がAO＋ブルーム＋SMAA、標準がブルーム＋FXAA、軽が膜の合成だけ。

### 画面空間の名札（S7）

名前・ゲージ・バフ3つの7要素を1つの名札とし、毎フレームtransformだけを書いた。GPUありの1080pで、CPUは名札0個の2.7msから、300個で3.3ms、600個で3.6msになり、どれも60fpsを保った。奥行きで`z-index`を並べ替え、変わったときだけ書く。名札の根に付けた`will-change: transform`はGPUなしの端末で重くなるおそれがあるので、段階7で付けるかどうかを測る。

## 後回しにしたこと

- 画面空間のHUD（名札・ゲージなど）と、その根のtransformだけを毎フレーム書く`HudFrameService`は、載せる物ができる段階7で作る。段階5では、置く物のない層だけを先に作ることはしなかった。
- 品質の表（`table-3d-quality.ts`）は作ったが、個人の設定として選ぶ画面と、描画への反映は段階10で足す。
- `visual-webgpu`・`visual-webgl2`の撮影は、描く物がそろう段階14で始める。
- 地形の灯りによる陰りと、暗闇と霧のテクスチャ（maskNode・MRTの膜）は段階9で扱う。それまでは盤の暗闇と霧をCSSの重ねが上に描く。
- 地形の面をWorkerで組む処理は、チャンクの作り直しが重いと分かってから入れる。
- e2eで`elementFromPoint`を使う6か所（`see-through`・`hex-pedestal`・`terrain-batch`・カットイン2つ）は、CSSの卓の当たり判定そのものを確かめている。コマが当たり判定に入る段階7で、索引に問う形に書き直す。
- 重なったコマのメニューは、今も`TabletopOverlapService.findAt`でページの要素から集めている。段階7で当たり判定の`allAt`に置き換える。
- 押した場所が何もない卓かどうかを、押下の要素で決めている所がある（卓のジェスチャー、移動の計画、画像のドロップの的）。canvasで描くと押下の要素が変わるので、段階5で当たり判定とcanvasを組み合わせて決める形に直す。
- `e2e/background-backdrop.spec.ts`は背景の奥のずれをtransformから読む。このずれはCSSの卓だけの挙動なので、段階10で本物の3Dに置き換えるときに書き直す。

## 気にかけておくこと

- initialの大きさは段階2の時点で3,097,817バイト（`--stats-json`から、mainとpolyfillsが静的に読む範囲をたどって数えた）で、段階3で警告の3,100,000を3.48KB、段階4で9.31KB超えた。起動時に作る組み込みエフェクトの見本（32.5KB）を遅延へ移すことも考えたが、同期オブジェクトなので、ほかの端末から届く同じ識別子との前後が変わるおそれがあり見送った。このブランチは最後に1回だけ出すので、途中の段階では警告を超えてよいことにし、段階15（CSS 3Dのコマのコンポーネントが消える）でmain以下に戻すことを完了条件にする。
- 段階2の確認で、vitestの全件を流したとき`hotbar-slot-editor.component.spec.ts`の2件が1回だけ落ちた。単独でも、続けて2回流した全件でも通った。メモリの空きが2GBまで減っていたときで、今回の変更とは関係しない。もう一度出たら原因を追う。
- SafariとFirefoxでWebGPUとWebGL2が使えるかは、ユーザーの判断でいったん確かめないことにした（2026-10-31）。確認ページは残してあるので、必要になったら各端末で開いてもらう。
